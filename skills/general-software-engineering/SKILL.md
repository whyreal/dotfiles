# 通用软件工程原则

> 本规则是对 [code-design](../code-design/SKILL.md) 的补充，前者侧重具体编码规范，此处侧重设计原则与决策依据。

## 单一职责原则（SRP）

- **一个函数只做一件事**：如果一个函数需要拆成多个段落并用空行分隔，它就应该拆成多个函数
- **一个模块只承载一类业务能力**：模块改名需要用"和"字连接时（如"搜索和导航"），说明需要拆分
- **判断标准**：用一句话描述函数职责，如果出现"和"、"或"、"先...再..."，则违反 SRP

## 函数长度与复杂度

- **单函数不超过 50 行**（不含空行和注释），超过应拆解
- **嵌套不超过 3 层**：`if` 内套 `if` 内套 `if` 是极限，超过需用卫语句、策略模式或提前 return 扁平化
- **条件分支不超过 5 个**：`if/else if` 链超过 5 个分支用策略模式或配置驱动替代

## DRY（Don't Repeat Yourself）

- **重复出现 3 次以上的代码片段必须提取**：包括但不限于 try/catch 块、字段映射、数据转换
- **重复的模式**：如果两处代码结构相同只是参数不同，提取为函数
- **例外**：测试代码中允许适度重复以保持可读性

## 组合优于继承

- 优先使用组合（props + slots + emit）复用 UI 逻辑
- 优先使用高阶函数（higher-order function）复用业务逻辑
- 仅在需要"is-a"关系时使用继承

## 避免过度抽象

- **YAGNI（You Ain't Gonna Need It）**：不要为未来可能出现的需求提前抽象，等到确实需要时再重构
- **第三次才抽象**：通用逻辑第一次直接写，第二次容忍重复，第三次再提取为公共模块
- **过度抽象的信号**：抽象层比实际业务代码还复杂、需要大量注释解释抽象的目的

## 最小依赖原则

- **禁止链式调用**：`a.getB().getC().doSomething()` 暴露了内部结构，封装为 `a.doSomething()`
- **依赖方向**：模块 A 依赖 B 时，B 不能反向依赖 A；跨层依赖必须单向（见 vue-ddd 的分层规则）
- **引入门槛**：引入一个新的 npm 包前，先问自己 —— 能否用 20 行原生代码实现？

## 常量与配置

- **不要等"多个地方用到"才提取常量**：魔法值（magic number/string）出现时就应定义为常量，为后续维护建立锚点
- **配置集中**：同一业务域的所有常量放在同一文件中，按用途分组，用注释说明上下文
- **常量命名**：`SCREAMING_SNAKE_CASE` 表示全局静态常量，普通模块级常量用 `camelCase`

## 命名驱动设计

- **命名是代码最重要的文档**：变量/函数/模块的名字应准确表达其职责和返回值
- **长度与作用域正相关**：作用域越大，命名越完整；10 行内的闭包变量可以用短名
- **命名自查清单**：
  - 布尔值用 `is`/`has`/`should`/`can` 开头
  - 函数名用动词开头（`get`/`set`/`create`/`handle`/`fetch`）
  - 避免通用词（`data`/`info`/`result`/`temp`），除非在极窄作用域内
